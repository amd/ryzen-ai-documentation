Compiled Model Output
======================

After successful compilation, the AMD Vitis™ AI Execution Provider generates compiled model artifacts in the ``cache_dir/cache_key`` directory. These files contain all the necessary binaries and metadata required for model execution on the NPU at runtime.

Understanding the Compiled Model
---------------------------------

When you compile a model, the entire directory structure created in ``cache_dir/cache_key`` constitutes your compiled model. All files within this directory are required for runtime inference.

**What gets created:**

- Binary files optimized for NPU execution
- Model metadata and configuration
- Runtime execution graphs
- Compilation logs and summary reports

Directory Structure
-------------------

After compilation, your ``cache_dir`` contains the following structure:

**Flat-Buffer Format (.rai file - Default):**

.. code-block:: text

   cache_dir/
     cache_key.rai                  # Single packaged model file

**Directory Structure Format:**

.. code-block:: text

   cache_dir/
     cache_key/
       vaiml_par_0/
         # Compiled model files
       final-vaiml-pass-summary.txt  # Compilation summary report
     [additional compilation artifacts]


Model Storage Formats
---------------------

The compiler supports two storage formats for the compiled model:

**Flat-Buffer Format (.rai file)**
^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^

  A single ``.rai`` file that packages all model artifacts in a compact binary format. This format uses memory-mapped file loading for efficient zero-copy access.
  
  **What to copy to the board:** Copy only the single ``.rai`` file to your target board.
  
  **When to use:** 
  
  - For production deployment
  - When transferring models to target hardware
  - For large models where single-file management is easier
  - When you need faster loading times

**Generating the Flat-Buffer Format**

The ``.rai`` file is generated by default by the Vitis AI compiler during model compilation. No special option is required in this case.


Directory Structure Format
^^^^^^^^^^^^^^^^^^^^^^^^^^^

The compiled model is stored in ``cache_dir/cache_key`` as a directory hierarchy containing the following:

- ``vaiml_par_0/`` - Partition subdirectory containing NPU-specific binaries and runtime files
- ``final-vaiml-pass-summary.txt`` - Compilation summary with performance metrics
- Model metadata and intermediate compilation artifacts (useful for debugging)

**What to copy to the board:** Copy the entire ``cache_key`` directory to your target board, maintaining the directory structure.

**When to use:** 

- During development and debugging
- When you need to inspect compilation artifacts
- When you want detailed logs and reports

**Generating the compiled cache directory**

The compiled cache directory is retained only when the ``keep_outputs`` debugging option is set in the ``vaiml_config`` section of the configuration JSON file. Use this option only when you need to debug an unexpected failure (see :doc:`ep-config-file`).

.. code-block:: json

   "vaiml_config": {
     "keep_outputs": true
   }

Compilation Summary Report
---------------------------

After compilation, you can review detailed compilation results in the summary report.

Viewing the Compilation Summary
^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^

To view compilation details, display the content of the summary file:

.. code-block:: bash

   cat cache_dir/cache_key/final-vaiml-pass-summary.txt

Compilation Settings
^^^^^^^^^^^^^^^^^^^^

The **Compiler Information** block records the target and the configuration used
for this compilation.

.. list-table::
   :widths: 30 70
   :header-rows: 1

   * - Setting
     - Description
   * - **Target Device**
     - Target NPU device (for example, ``stx`` for Strix devices)
   * - **Device Data Type**
     - NPU execution precision (for example, ``bfloat16``)
   * - **Model data type**
     - Original model precision (for example, ``float32``)
   * - **NPU Frequency**
     - NPU clock frequency, in MHz, assumed by the compiler when scheduling the model
   * - **Optimize Level**
     - Optimization level applied; higher levels trade compile time for runtime performance
   * - **Logging Level**
     - Verbosity of the compiler log (for example, ``info``)
   
Key Metrics Explained
^^^^^^^^^^^^^^^^^^^^^

.. list-table::
   :widths: 30 70
   :header-rows: 1

   * - Metric
     - Description
   * - **Model signature**
     - Unique hash identifying your model
   * - **Number of operators**
     - Total operators in your model
   * - **GOPs**
     - Giga Operations - computational complexity measure
   * - **Operators supported by VAIML**
     - Percentage of operators that can run on NPU
   * - **GOPs supported by VAIML**
     - Percentage of computation that can run on NPU
   * - **Number of subgraphs supported by VAIML**
     - Subgraphs the Vitis AI compiler is able to compile
   * - **Operators offloaded by VAIML**
     - Operators actually running on NPU (after optimization)
   * - **GOPs offloaded by VAIML**
     - Computation actually running on NPU (after optimization)
   * - **Number of subgraphs offloaded by VAIML**
     - Model partitions created for NPU execution
   * - **Number of partitions offloaded to NPU**
     - Partitions dispatched to the NPU at runtime
   * - **Number of partitions executed on CPU**
     - Partitions that remain on the CPU execution provider
   * - **Subgraph type**
     - Execution target: ``npu`` or ``cpu``
   * - **OPs**
     - Absolute operation count for the subgraph
   * - **fp32 ops %**
     - Share of the subgraph's operations that originate from float32 operators
       before conversion to the device data type
   * - **Total**
     - End-to-end wall-clock compilation time

.. tip::

   Compilation results are cached against the **Model signature**. Recompiling
   an unchanged model reuses the cached artifacts and completes far faster than
   the initial build.

Interpreting Compilation Results
^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^

**Optimal Compilation (100% NPU offload):**

.. code-block:: text

    Number of operators offloaded by VAIML: 122 (100.000%)
    GOPs offloaded by VAIML: 7.770 (100.000%)
    Number of subgraphs offloaded by VAIML: 1
    Number of partitions offloaded to NPU: 1
    Number of partitions executed on CPU: 0

This indicates all operations run on the NPU for maximum performance.

**Partial NPU Offload:**

.. code-block:: text

   Number of operators offloaded by VAIML: 87 (71.596%)
   GOPs offloaded by VAIML: 5.327 (68.560%)
   Number of subgraphs offloaded by VAIML: 2
   Number of partitions offloaded to NPU: 2
   Number of partitions executed on CPU: 1
   Number of subgraphs with compilation errors (fall back to CPU): 1

This indicates some operations fall back to CPU execution. Check the reasons:

- **Compilation errors:** Subgraph failed to compile for NPU
- **Above max subgraphs (7):** Too many partitions, excess falls back to CPU

Details on model deployment on the board can be found in :doc:`../model_deployment/setup-hw`.

Compiler Stack Size Requirement
^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^

The Vitis AI compiler requires sufficient stack space to run. If the available
stack size is too small, the compiler stops and reports an error indicating
that the failure may be due to inadequate stack size.

In this situation, the compiler may emit the following message in the output
log:

.. code-block:: text

   Please check the output log for errors and fix those before you run the application. If a stack trace is printed above, refer to it for debugging. If no stack trace or errors are visible, the issue may be caused by insufficient stack size. To increase the stack size, execute the command 'ulimit -s unlimited' and re-run the compiler.
   Compilation Failed
   (WARNING:0, CRITICAL-WARNING:0, ERROR:1)

This message is generated by the compiler and indicates that you should:

1. Inspect the output log for explicit errors or stack traces.
2. If no clear cause is visible, increase the stack size, for example by
   running:

   .. code-block:: bash

      ulimit -s unlimited

   and then re-run the compiler.
